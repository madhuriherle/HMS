This is a proposed comprehensive table inventory. Some supporting tables are optional and can be combined or omitted depending on the final business rules and implementation decisions.

### Important relationship rules

* `members` is the central person record. Receipts, memberships, KYC requests, service records, and activity history should reference it using foreign keys.

* `member_memberships` references `membership_types`; price history references `membership_type_prices`.

* `receipt_allocations` connects receipts to members and, when relevant, their membership transactions.

* Magazine label generation should combine eligible members, affiliates, associates and press/media recipients while applying delivery preferences, pause periods, receipt requirements and return indicators.

* Committee and event participants should link to `members` when the person is an existing member, without duplicating their personal details unnecessarily.

* Approval and audit records should retain the actor, decision, timestamp and reason. Sensitive records should not be permanently erased without checking retention and audit requirements.

Recommended next step: Finalize the relationships, constraints, and status values for these tables, then create the PostgreSQL ER diagram and SQLAlchemy models before beginning the FastAPI endpoints and React screens.
















Understood. For HMS MMA, every table should have standard audit columns, not just the main membership tables.

## 2. Common PostgreSQL audit definition

Apply these columns to all 69 tables listed below.

SQL

```
created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
created_by  BIGINT NULL REFERENCES users(id),
updated_at  TIMESTAMPTZ NULL,
updated_by  BIGINT NULL REFERENCES users(id),
deleted_at  TIMESTAMPTZ NULL,
deleted_by  BIGINT NULL REFERENCES users(id),
is_deleted  BOOLEAN NOT NULL DEFAULT FALSE
```

Implementation notes:

* `created_by` and `updated_by` reference the user who performed the action. They may be `NULL` for system-generated records or during initial system setup.

* `updated_at` and `updated_by` should be updated together whenever a record changes.

* For soft deletion, set `deleted_at`, `deleted_by`, and `is_deleted = TRUE`.

* For permanent deletion, apply retention and dependency rules before removing data.

* The application should enforce audit behavior centrally in SQLAlchemy services or event handlers. Do not rely only on React to provide audit values.

* For audit logs, record the actual actor and event details, and restrict updates and deletes.

## 18. Audit implementation rules

One important PostgreSQL detail: if `created_by` references `users.id`, the `users` table has a self-referencing foreign key for its audit fields. This is supported, but migrations must create the users table before other tables that reference it.

For activity logs, delivery logs, approval history and similar historical records, keep the common audit columns but enforce append-only behavior. A log entry's `created_at` and `created_by` describe when and by whom that log was recorded; its business event timestamp and actor fields describe the event itself.

Final structure: 69 proposed tables, each with the common audit columns, with PostgreSQL foreign keys, constraints, and JSONB fields where appropriate. The next step is to turn this inventory into an ER diagram and ordered PostgreSQL migrations, resolving optional tables and business rules before implementation.

# HMS MMA – Complete Application Flow

The HMS MMA (Havyaka MahaSabha Membership Management App) can be understood as a connected workflow: configure the system → register members → collect receipts → approve memberships → manage magazine delivery → handle services and events → send notifications → generate reports.

The database migration provides the tables to support these modules. The flow below explains how the modules work together from a user’s point of view.


## 1. Overall system flow

## 1. Masters & System Setup

Configure locations, membership types, prices, services, document types, roles and permissions.

## 2. User & Access Management

Create users, assign roles and control which modules each role can access.

## 3. Member Registration

Register members online or offline, validate duplicates, capture documents and create membership records.

## 4. Receipt & Membership Approval

Record payments, allocate receipts, review applications and approve memberships.

## 5. Member Services & Operations

Manage magazine delivery, labels, returns, KYC, profile changes, events, affiliations, associates, press and committee records.

## 6. Notifications, Reports & Activity

Send WhatsApp notifications, track user and member activity, and generate operational reports.

## 2. Detailed module-by-module flow

### Step 1 — Masters setup

The administrator configures the data used throughout the application.

1. Import or maintain Indian states, districts, taluks and postal codes.

2. Map postal codes to their corresponding locations.

3. Create membership types and configure their prices.

4. Configure document types, service types and system settings.

5. Create roles and permissions for administrators, staff and other users.

Why this comes first: Registration forms and other modules depend on these master records.

### Step 2 — User management

1. Create a staff login.

2. Assign one or more roles.

3. Configure permissions for viewing, creating, editing, approving or deleting records.

4. Record login/logout and relevant user actions in the activity log.

For example, a staff member might be allowed to register members but not approve them. The application should enforce that distinction in the backend as well as the UI.

### Step 3 — Member registration

Registration workflow

* Start registration

  A member is registered online or by staff through the offline registration form.

* Enter member details

  Capture personal details, contact information, address, location, membership type and required documents. Support English and Kannada.

* Validate the application

  Check required fields and possible duplicate members before creating the record.

* Create membership records

  Store the person's information and the associated membership application or membership record.

* Continue to receipt and approval

  The application proceeds through the relevant payment and approval steps.

### Step 4 — Receipt and payment flow

The receipt module records payments and links them to members or other relevant transactions.

1. Create an online or offline receipt.

2. Record receipt items, payment information and applicable membership charges.

3. Allocate the receipt to the relevant member or members.

4. Maintain cancellation or refund records when applicable.

5. Make receipt allocations available to reports and magazine label processing.

Important distinction: A receipt records a financial transaction. Membership approval is a separate business action, so the system should not automatically treat payment as approval unless that is an explicitly configured rule.

### Step 5 — Membership approval and number assignment

## Approval process

1. Authorized staff review the member's application and documents.

2. They approve or reject the application, or return it for corrections.

3. Record the decision, user, date and relevant remarks in the approval history.

4. When the required approval conditions are met, assign the permanent membership number.

5. Update the member's status and make the approved member available to the relevant operational modules.

The application should preserve the distinction between a pending application and an approved member.

### Step 6 — Member profile and ongoing changes

After registration, the member profile becomes the central place for that member's information.

It can bring together:

* Personal and address details.

* Membership type and membership history.

* Receipt and payment information.

* Documents and KYC records.

* Magazine delivery status and returns.

* Service usage and linked events.

* Profile changes, approval history and activity timeline.

For profile changes, a member or authorized staff member submits a change request. The request is reviewed, approved or rejected, and the profile history records the resulting change.

For membership type changes, the system records the old and new types, maintains the change history, and links any required new receipt or payment.

### Step 7 — KYC flow

1. Create a KYC request for a member.

2. Notify the member or responsible staff that documents or information are required.

3. Collect and submit the requested information.

4. Review the submission and approve it or request corrections.

5. Retain the KYC request and its review history.

KYC is an ongoing process, so it should be possible to create a new request when another verification cycle is required.

### Step 8 — Magazine delivery and labels

## Magazine delivery workflow

1. Set up magazine delivery for eligible members, affiliations, associates or press/media records.

2. Apply the delivery preferences, including start/stop settings and pauses.

3. Prepare label batches using the selected district, taluk and eligible member criteria.

4. Generate labels for the selected batch and track which records have been included.

5. Record returned magazines and associate the return information with the relevant profile and delivery records.

Example

If a member's magazine delivery is paused, the pause record should include the relevant note and dates. That member should be handled according to the configured eligibility rules when the next label batch is prepared.

### Step 9 — Events

1. Create an event with its name, date, location and other details.

2. Add guests, honorees and participating members.

3. Upload invitations or supporting attachments.

4. Link the event to relevant member profiles.

5. Use event information as a source for notifications and event-related reporting.

### Step 10 — Affiliations, associates, press/media and committee

These are related operational modules, but they represent different kinds of records.

### Step 11 — WhatsApp notifications

## Notification flow

1. Configure approved message templates.

2. Select recipients individually, through filters, or through a bulk recipient list.

3. For imported phone numbers, upload a CSV and validate the records.

4. Prepare the notification campaign and select the applicable template.

5. Send the messages through the configured provider.

6. Store recipient-level delivery information and message logs for tracking.

For example, an approved member could receive an activation notification using the configured activation template. Individual custom messages and bulk notifications should follow the relevant template and provider requirements.

### Step 12 — Reports and activity tracking

Reports use data from the operational modules, including:

* Unapproved members.

* Approved member lists with configurable English/Kannada fields.

* District, taluk, gender and membership-type reports.

* Pending and generated magazine labels.

* Magazine returns and delivery records.

* Receipt-wise member lists and receipt reports.

* Activity and event-related records.

The activity area should provide two useful perspectives:

* User activity: logins, logouts and relevant create, update and delete actions.

* Member timeline: registration, approvals, service usage, profile changes and other significant member events.

## 4. What the statuses should mean

Because the database design includes a general `status` field as well as workflow-specific statuses, they should have clearly defined meanings.

|
Record type

|

General status

|

Separate workflow state

|
| --- | --- | --- |
|

Member

|

Whether the record is active, inactive or otherwise retained

|

Application approval and membership state

|
|

Receipt

|

Whether the receipt record is active or cancelled/retained

|

Payment or refund processing state

|
|

Magazine subscription

|

Whether the subscription record is active

|

Delivery, pause or stop state

|
|

KYC request

|

Whether the request record is active

|

Pending, approved, rejected or correction required

|
|

Profile change request

|

Whether the request record is active

|

Pending, approved or rejected

|
|

Notification campaign

|

Whether the campaign record is active

|

Draft, queued, sending or completed, as applicable

|

These are recommended status responsibilities, not a claim that every value or transition has already been implemented in the migration. The allowed values and transitions should be defined consistently in the application and database.

## 5. Example: One member's journey

* Staff registers a new member and uploads the required documents.

* The system checks for duplicates and creates the application.

* A receipt is created and allocated to the member.

* An authorized reviewer approves the application and the permanent membership number is assigned when applicable.

* The member profile displays membership, receipt and approval information.

* Magazine delivery is configured, and the member can be considered for eligible label batches.

* The member may later submit KYC or profile-change requests, attend linked events, or use recorded services.

* Relevant notifications, activity history and reports are updated as these actions occur.

In short: the member record is the central entity. Registration creates the record; receipts, approvals, KYC, delivery, events and profile changes connect to it; notifications communicate relevant updates; and reports bring the operational data together. The foreign keys should enforce those relationships so records remain connected and traceable.













# HMS MMA – Complete API List (CRUD + Workflow)

Below is the API checklist for your React JS + FastAPI + PostgreSQL application. It covers the CRUD operations for all the modules, along with the additional workflow APIs needed for approvals, payments, magazine delivery, notifications, reports and activity tracking.

API convention: use `/api/v1` as the base path. The examples use REST-style endpoints, with `GET` for reading, `POST` for creating or performing actions, `PATCH` for partial updates, and `DELETE` for deletion.

## 16. API implementation rules

Use these rules consistently across all modules:

1. Authentication: Protect private APIs with authentication. Enforce role and permission checks in FastAPI, not only in React.

2. Validation: Validate request bodies, IDs, file types, required fields and related database records.

3. Pagination: Return pagination metadata for large lists.

4. Transactions: Use database transactions for operations that change multiple related tables, such as approving a membership and assigning its number.

5. Deletion: Use soft deletion where records must remain for audit, payment, membership or legal history. Permanent deletion should be restricted.

6. Audit fields: Populate `created_by`, `updated_by` and relevant deletion fields from the authenticated user, not from untrusted frontend values.

7. Status values: Define allowed status values and transitions separately for each workflow. Do not use one ambiguous status field for unrelated processes.

8. File access: Check permissions before returning document or attachment download links.

9. Errors: Return consistent error responses, including validation details and useful messages.

10. Documentation: Enable FastAPI OpenAPI/Swagger documentation and describe each endpoint's request body, response model, permissions and error codes.

## 17. Recommended development order

* Phase 1 – Foundation

  Authentication, users, roles, permissions, settings and location masters.

* Phase 2 – Membership

  Registration, duplicate validation, member profiles, documents, approval, membership numbers, KYC and change requests.

* Phase 3 – Financial operations

  Receipts, receipt items, allocations, online payments, cancellations and refunds.

* Phase 4 – Magazine operations

  Subscriptions, delivery settings, pauses, returns, batches and labels.

* Phase 5 – Other management modules

  Events, affiliations, associates, press/media and managing committee.

* Phase 6 – Communication and reporting

  WhatsApp campaigns, imports, delivery logs, reports, exports and dashboards.

* Phase 7 – Audit and hardening

  Activity history, approval workflow configuration, access-control testing, error handling and API documentation.

Final answer

The earlier list covers the main modules and their CRUD operations, but it is a proposed API inventory—not a verified, exhaustive list of every endpoint your application needs. Before development is considered complete, compare it against each database table, screen, permission, and business workflow. Internal tables such as history, relationship, token and logging tables should not automatically receive unrestricted CRUD endpoints.
