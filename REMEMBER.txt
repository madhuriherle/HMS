RULE 1: MEMBER RECORD ID (id) vs. PERMANENT MEMBERSHIP NUMBER (member_code)
--------------------------------------------------------------------------------
1.1  DATABASE RECORD ID (Member.id):
     - An internal auto-increment primary key (e.g., 1, 2, 7, 9).
     - Used ONLY for foreign keys and internal database lookups. IT IS NEVER SHOWN ANYWHERE ON A
       SCREEN (28-Oct-2026, the user's order): no "ID: 7", no "App ID", no "Record ID", no
       "Registration Number", no "Application ID", no "Tier ID" / "Account ID". A person is shown by
       name and membership number; an unapproved applicant by name, mobile and source only.
     - NEVER display, label, or treat Member.id as "Membership No", "Member ID",
       "MID", or "Member Code".
     - NEVER fall back to Member.id if a member has no membership number.
       If a member is not approved or has no code, the membership number is EMPTY.

1.2  PERMANENT MEMBERSHIP NUMBER (Member.member_code / Member.membership_number):
     - The official, permanent Sabha membership code (e.g., "12345", "LM-007", "HM-2026").
     - Given ONLY upon official approval or through historical CSV/migration import.
     - Stored in Member.membership_number (with member_code as alias/synonym) and
       MemberMembership.membership_number.
     - Online / Unapproved applicants DO NOT have a permanent membership number
       until they are approved!

1.3  FRONTEND API ADAPTER RULE:
     - In normalizeMember (frontend/src/utils/apiAdapters.js):
       membershipNumber MUST strictly be:
       firstDefined(member.member_code, member.membership_number, member.membershipNumber, '')
       NEVER append `, member.id` as a fallback!

1.4  MEMBERSHIP NUMBER RETRIEVAL & ASSIGNMENT:
     - Across all components (Receipt Entry, Receipt Tracking, Member Lookup, Global Search, etc.),
       always inspect both `member.membership_number` and `member.member_code`
       (e.g., `member.membership_number || member.member_code || member.membershipNumber || ''`).
     - In Receipt Entry, clicking "Assign" from the Membership List must populate the
       form's `membershipNo` with the approved member's permanent number and display `#<number>`.
     - Backend endpoints serializing dictionary rows or plain models must ensure both
       `membership_number` and `member_code` are populated for approved members.

RULE 2: MEMBER vs. USER SEPARATION
--------------------------------------------------------------------------------
2.1  A MEMBER IS NOT A SYSTEM USER:
     - A "User" is an administrative person logging into this back-office system
       (Super Admin, Admin, Manager, Accountant, Operator, Data Entry).
     - A "Member" is a registered community person in the Sabha directory.
     - Members DO NOT have portal login access or user accounts created for them.
     - NEVER auto-provision a User record when registering or approving a Member.
     - In User Management, NEVER display Members or assign them back-office roles.

2.2  FAMILY MEMBERS MAY SHARE ONE MOBILE NUMBER:
     - A mobile number is NOT unique among members (migration 0077 drops the unique index).
     - Registration never rejects a mobile that is already in use. The form shows a note listing
       the members who already use it, and the operator carries on.
     - A duplicate Kannada name + same date of birth is still rejected (409).

RULE 3: RECEIPT ENTRY & ALLOCATION (LINKING)
--------------------------------------------------------------------------------
3.1  DIRECT LINKING ON RECEIPT ENTRY:
     - If a member is selected or an entered member exists in Receipt Entry:
       The receipt MUST be directly linked via ReceiptAllocation on Save.
     - NEVER discard the member allocation based on route source.
     - An unapproved applicant is linked via member_id (ReceiptAllocation.member_id = 7).
       Their Membership No box remains BLANK because they do not have a permanent
       membership number yet.
     - Once linked:
       * Whether applicant or approved member -> Receipt status = "ASSIGNED"
     - A receipt linked at entry MUST NEVER be left as "UNASSIGNED".

3.2  RECEIPT & TRANSACTION DATES (NO FUTURE DATES):
     - Receipt Date (Receipt.receipt_date) MUST NEVER be in the future. Money cannot
       be received on a future date. Enforced in schema validator and frontend DateInput.
     - Transaction Date (Receipt.transaction_date) MUST NEVER be in the future.
     - On frontend DateInput, pass max={getTodayISODate()} for both fields so the
       calendar picker physically disables future dates, and validate immediately.
     - Service / Booking period dates (From Date / To Date) CAN be in the future (e.g.
       advance Hall / Kalyana Mantapa bookings or festival sevas).

3.3  MULTI-LINE PARTICULAR ITEMS & "ADD ITEM":
     - The first particular row is the primary item; "Add Item" is ONLY for receipts
       covering multiple distinct heads (e.g., Membership + Donation).
     - The "Add Item" button sits at the BOTTOM beneath all item rows, NEVER squeezed
       into the top-right corner of Row 1.
     - "Add Item" MUST NOT allow adding an empty row if the current/previous item's
       amount is empty or not > 0.
     - DUPLICATE PARTICULARS ARE BLOCKED: A receipt cannot have duplicate lines for
       the same particular (or same particular + sub-type). Form validation rejects
       duplicates with an explicit instruction to combine amounts into one line.

3.4  STRICT SEPARATION OF RECEIPT STATUS VS MEMBER STATUS:
     - Receipts have ONLY THREE statuses:
       * UNASSIGNED: Receipt created without any member/applicant allocation.
       * ASSIGNED: Receipt linked to an applicant or approved member.
       * CANCELLED: Spoiled/void paper receipt (zero amount, preserves sequence number).
     - "APPROVED" IS STRICTLY A MEMBER STATUS (Member.approval_status), NEVER A RECEIPT STATUS.
     - Receipts MUST NEVER be labelled "APPROVED". A receipt is only about money and whether
       it is mapped to a person (ASSIGNED) or unmapped (UNASSIGNED), or void (CANCELLED).
     - Membership List displays already-approved members, showing their standing
       ("Active" / "Inactive"). No redundant "Approved" badges.
     - Unapproved Memberships displays applicants awaiting approval, showing their receipt
       assignment status ("Receipt Assigned" vs "Receipt Unassigned").

RULE 4: BULK RECEIPT AUTO-MAPPING RULES
--------------------------------------------------------------------------------
4.1  PURPOSE OF BULK AUTO-MAPPING:
     - The Bulk Auto-Mapping queue is STRICTLY for unassigned receipts (e.g., legacy
       receipt imports, bank reconciliation deposits) that have NO member link yet.
     - Receipts already linked to a member MUST NOT appear in this queue.

4.2  STRICT MATCHING RULE:
     - Matching is strictly:
       Receipt.payer_membership_no  <===>  Member.member_code (Permanent Membership No)
     - NEVER match Receipt.payer_membership_no against Member.id (database primary key)!
     - If receipt has entered member number "12345", it matches ONLY members whose
       permanent membership number is "12345".
     - Do not use fuzzy guessing (no multi-tier phone/name auto-linking). Matching
       is exact on the official permanent member code.

4.3  MANUAL "PICK MEMBER" MODAL:
     - If a receipt cannot be auto-matched, clicking "Pick Member" allows the admin
       to search live members by name, phone, or member code via /api/v1/members/?search=...
     - When a member is picked, display their permanent Member Code, NEVER fallback
       to "MID #id".

RULE 5: UI & DISPLAY STANDARDS
--------------------------------------------------------------------------------
5.1  LABELS AND TEXT:
     - Unapproved list: no id is shown (name, mobile and source only).
     - Approved list: Label as "#12345" (Permanent Membership Number).
     - Never use the term "MID" as it confuses users between "Member ID" and
       "Membership Number".
     - In receipt printouts / PDFs: If unapproved, do not print a fake membership
       number; print Membership No only when Member.member_code exists.

5.2  SELECTION MODE IN TABLES:
     - Do not permanently clutter tables with empty checkbox columns when users
       are doing row-by-row actions.
     - Keep tables clean with dedicated action buttons (View, Edit, Approve, Reject).
     - Provide a "Select" toggle button in the header bar to activate checkboxes
       for batch operations when needed.

RULE 6: NUMBERING (RECEIPTS AND MEMBERSHIP NUMBERS)
--------------------------------------------------------------------------------
6.1  RECEIPT NUMBER:
     - Default format is a plain 4-digit running number (0001, 0002 ...) with no year
       in it, restarting every financial year. The format is a setting (Number Formats);
       never hard-code a receipt number pattern in the frontend.
     - The financial year always comes from the RECEIPT DATE (1 April - 31 March). There
       is no separate FY setting.
     - A receipt number is unique per (financial_year, receipt_number) among live rows
       (index uq_receipts_fy_number_active). The same number may exist in different years.
     - Receipt Entry checks the typed number as the person types (GET /receipts/number-check)
       and again when the date changes; the server check on save is the final guard.
6.2  MEMBERSHIP NUMBER: one permanent number per member, minted at approval from
     Number Formats (MEMBER_CODE). It is copied to MemberMembership.membership_number.
6.3  A RECEIPT IN THE RECYCLE BIN KEEPS ITS NUMBER. The Delete button is a soft delete: the receipt can
     be restored, so its number is not offered again and cannot be typed for another receipt (the
     message names the Recycle Bin). Only a PERMANENT delete (purge) gives the number back, and the
     series then carries on from the highest receipt that still exists in that financial year. A
     cancelled receipt keeps its number too.
6.4  RECEIPT ENTRY OPENS ON TODAY'S DATE (so a new open or Reset suggests the current financial year's
     0001). Save & New keeps the date just used, so old receipts can be entered one after another. The
     Receipt Tracking footer counts Assigned, Unassigned and Cancelled separately by real status.

6.5  THE NUMBER RECEIPT ENTRY OFFERS COMES FROM THE OFFICE'S OWN SERIES ONLY. Receipts imported from the old register
     (source OLD_REGISTER or UNAPPROVED_IMPORT) are never counted when the next number is worked out
     (services/numbering._legacy_highest): the paper books have several series and typing mistakes (one receipt was 725600
     for 72560 and made Receipt Entry offer 725601). A number already taken is still skipped. The register's own numbers are
     corrected on the receipt itself.

RULE 7: LOOKUPS
--------------------------------------------------------------------------------
7.1  Every "verify / find by number" lookup (/members/lookup, /receipts/member-lookup,
     family and referral number checks, Receipt Entry Membership No. box) accepts the
     REAL MEMBERSHIP NUMBER ONLY. A bare id (7), a REG-2026-0007 style number or a
     mobile number must find nobody.
7.2  An unapproved applicant has no membership number, so they are picked from the lists
     and linked by member id; they cannot be found by typing a number.

RULE 8: MEMBERSHIP TYPE AND CREDIT
--------------------------------------------------------------------------------
8.1  Only money paid for the membership counts toward a member's type: receipt types
     MEMBERSHIP and TYPE_CHANGE (setting membership_credit.receipt_types). Donations,
     P.Nidhi, scholarship, magazine and event receipts NEVER change the membership type.
8.2  The type moves UP automatically when payments reach a higher type (today's prices). It moves
     DOWN automatically only when money is taken away: a receipt deleted, cancelled, refunded or
     un-assigned. Then, if the remaining payments no longer pay for the type held, the member goes
     to the highest type those payments pay for, judged at the prices of the day they began
     holding the type (joining day, or the day of the last change of type), never at today's
     price. Nothing else lowers a type (not a price change, not a recalculation).
8.2a A member whose payments fall short of the price of their joining era (an old receipt is
     probably missing: see Membership List > Payment mismatches) is FROZEN: no automatic change
     either way, and a removal of money does not lower them. Adding the missing receipt, even as an
     Old receipt (dummy, number typed in the OLD- format from Number Formats), clears the flag and
     the normal flow applies again.
8.3  Deleting a receipt that is assigned to a member removes its allocation from the
     member's history and lowers their credit, and the type follows by rule 8.2.
8.5  CREDIT COUNTS THE LINES, NOT THE WHOLE RECEIPT: the money that counts is the amount of
     the receipt's lines whose type is counted (Membership 500 + Donation 4500 counts 500),
     capped by what was allocated to the member. The order of the lines and the receipt's
     head type do not matter. Only receipts whose lines carry no known type fall back to the
     receipt type.
8.6  Editing a receipt re-checks the upgrade (a single allocation follows the credit lines).
     When a cancelled / deleted / refunded receipt or a removed allocation leaves the credit
     below the price of the member's type and nothing cheaper is paid for, the type stays and the
     approvers get an inbox notice "Membership type needs review" to decide.
8.7  A PARTICULAR SAYS FOR ITSELF WHAT IT IS - NEVER GUESS FROM ITS NAME. The MAIN particular carries two ticks
     (particulars.pays_for_membership, particulars.needs_description); its sub types follow it and carry
     neither (the server forces them off). When a receipt is saved each line copies "pays for membership" onto
     receipt_items.pays_for_membership (services/particular_flags.py, climbing from a sub type to its main
     particular), so changing a tick later never rewrites an old member's credit. Credit counts the lines with
     the tick; a line with no particular on record (an old receipt) counts by its line type against the saved list
     of counted receipt types (8.1). The Assign popup's "membership only" filter, "counts for membership" amount,
     the renewal mark and the Description box in Receipt Entry all read these ticks (no "Membership" / "Others"
     name checks anywhere). Migration 0087 ticked the existing main particulars whose name has "membership" in
     it; none is ticked "needs a description" (a particular with sub types gets its description from the sub type).
8.8  A RECEIPT LINE KEEPS ITS SUB TYPE BY ID: receipt_items.sub_particular_id (a child of the line's main
     particular, validated on save) plus sub_particular_name (the name as saved, so a rename never rewrites
     history). The description column holds ONLY a description someone typed (a main particular ticked "needs a
     description" and no sub type picked). Screens show the line as "Particular > sub type", reading
     sub_type and falling back to description for an old line that migration 0088 could not match (its
     description text did not equal a sub type's name). Receipt Tracking's sub type filter and filter list use
     the saved sub type name.
8.4  MEMBERSHIP TYPE PRICE: a type's price is a history of rows (MembershipTypePrice), not a
     field. The Amount on the Edit form and the Update Price screen use the SAME call
     (POST /masters/membership-types/{id}/prices): a changed amount is a new revision with a
     reason. Never save a type and silently drop its amount. A second change on the same day
     corrects that day's row and keeps a trail in the reason ("... (was 250.00)"). The list
     sends price_count so the revision badge shows the real number (1 = base price only).

RULE 9: DATA COMES FROM THE SERVER, NOT FROM THE FRONTEND
--------------------------------------------------------------------------------
9.1  No hard-coded dropdown lists, rules or sample data in the frontend. Fixed lists live
     in the lookup_values table (GET /meta/lists); limits and formats come from
     core/rules.py (GET /meta/rules); PIN prefixes from /meta/pin-prefixes; import
     templates from /meta/import-template/{kind}. No localStorage data, no fallbacks.
9.2  Phone numbers: digits allowed per country come from the phone_lengths list. India is
     exactly 10 digits and starts with 6, 7, 8 or 9. The field stops accepting digits at
     the country's maximum.
9.3  Dates are shown DD-MM-YYYY (formatDate), a date of birth is also TYPED that way (rule 16.12), and times 24-hour HH:MM; money as
     ₹1,234.00 via formatMoney (rupee sign, Indian grouping, two decimals).
     Downloads keep amounts as plain numbers.

RULE 10: MASTERS AND SCREENS
--------------------------------------------------------------------------------
10.1 There is NO separate Bank Master screen. Banks are created and listed from Payment
     Mode Setup, under its own privileges (masters.payment_modes.read / write / delete).
     A screen must never break because an unrelated module is switched off.
10.2 A disabled module is hidden from the sidebar and blocks its API for everyone.
10.3 The member profile loads one tab at a time: GET /members/{id}/profile/{section}
     (summary, overview, personal, contact, family, membership, receipts, magazine,
     events, history). Do not load everything in one call for the new screens.
10.4 Page layout: plain h1 heading (text-xl sm:text-2xl font-bold), no Back buttons, no
     big decorative icon blocks, normal site font sizes (text-xs / text-sm), no
     "card inside card" clutter. Registration amount and receipt date on a new
     registration are read-only (the amount follows the chosen membership type).

10.5 LISTS SHOW THE NEWEST FIRST (masters excepted, they keep their own order). A list endpoint
     with no sort given returns the newest record first (events: the latest event date first).
     The main lists also take sort_by and sort_dir (asc | desc): members, receipts and
     receipts/tracking, users, associates, press-media, affiliations, events and magazine
     subscriptions. sort_by must be one of the list's own column names (anything else is a 400),
     and ties fall back to the newest id. The helper is core/sorting.py (sort_query).

10.6 NEVER MORE THAN 200 ROWS IN ONE REQUEST, AND NEVER ALL OF A LIST AT ONCE. A list a person pages
     through is read from the server one page at a time (default 25; the choices are 25 / 50 / 100 / 200;
     core/pagination.LIST_PAGE_MAX = 200 caps a request). The SEARCH and EVERY FILTER are sent to the server
     and run on the whole table in the database, never on the rows already in the browser; the answer
     carries the total and the counts of the whole filtered set (summary), so footers and badges need no
     extra download. The sort is the server's too (rule 12.18). Use components/Pager.jsx for the controls and
     wait ~350 ms after typing before asking. An export asks page by page (200 at a time) or uses the
     export parameter. The filter drop-downs read their options from the server (for example
     GET /receipts/tracking-options), not from the rows on screen.
     Paged by the server now: Receipt Tracking, Membership List, Unapproved Membership, Assigned for
     Approval, Label List, Magazine (recipients, label and delivery batches, label batch detail,
     pauses and returns), Receipt Entry's two member lists and Payment Mode Setup (usage counts from
     GET /receipts/payment-mode-usage). The masters, roles, modules and privileges are reference
     data and keep their own limits. There is no "read everything" switch any more: a new list is
     built paged from the start.

10.7 A LIST OR POPUP GETS EVERYTHING IT SHOWS FROM ITS OWN API CALL. A member row carries its place
     (pincode, post_office_name, state_name, district_name, taluk_name) and its membership type and
     credit; GET /members/{id} carries the same place names; the Receipt Tracking filters come from
     GET /receipts/tracking-options (years, sub types, payment modes in use, active particulars,
     configured payment modes). A page never downloads a master list just to turn ids into names, and
     never makes a second call per row. The 15,000-row PIN table is never downloaded: the PIN lookup and
     autocomplete ask GET /masters/postal-codes?pincode_starts=... (searchPostalCodes / lookupPin in
     serverData.js). The small reference lists (states, districts, taluks, membership types, gothras,
     qualifications, particulars, payment modes) are read through serverData's cached loaders - kept in
     memory for five minutes, dropped on any write to /masters/, never put in browser storage.

RULE 11: HOW WE WORK (ALL AGENTS)
--------------------------------------------------------------------------------
11.1 Deploy to UAT only when the user asks. Never touch production unless the user explicitly asks
     for a prod update (then follow 11.9). Push to GitHub only when the user says push.
11.2 Alembic revisions are numbered in sequence and other agents add migrations at the
     same time: before creating one, list alembic/versions, take the next free number
     and confirm there is a single head (ScriptDirectory.get_heads()).
11.3 Run the backend tests (python -m pytest -q in backend) and the frontend checks
     (node scripts/check-undefined.mjs, node scripts/render-smoke.mjs, a vite build)
     before committing. Report failures honestly.
11.4 Never use git stash in the shared working tree. Preserve CRLF line endings when
     editing existing files.
11.5 When the user writes "tell me idea" (or asks "why / what / how"), answer with the
     proposal or the explanation FIRST, in short plain words, and build only after they say
     yes. Reference screenshots are for ideas: do not copy them exactly.
11.6 Other agents edit files at the same time. Never revert or reformat a file you did not
     change for the task; edit only the lines you need.
11.7 When the user pastes another agent's summary, it means: read the changes, run the checks,
     commit it and deploy it to UAT. Push to GitHub only when the user says push.
11.8 The top header of every panel page is layouts/MainLayout.jsx. components/Navbar.jsx is
     NOT used: a change to the signed-in user box (Profile, Log Out) goes in MainLayout.
11.9 PROD UPDATE, in this order, only when the user asks: (1) back up the prod database
     (pg_dump), the web folder, the code folder /opt/hms/repo and tag the running image;
     (2) restore the dump into a throwaway database on the UAT database server and run all
     migrations on that copy with the new code; check the real rows (members, receipts, users,
     roles) and run scripts/check_fk_orphans.py; (3) only if that is clean, upload the committed
     code to /opt/hms/repo/backend (the old folder is kept as backend.prev-*), rebuild with
     `docker compose up -d --build backend` in /opt/hms/prod (it runs alembic at start), replace
     /var/www/hms/prod with the same /api/v1 build UAT uses; (4) verify the site, the login
     route, the migration version and the row counts; (5) drop the throwaway database (it holds
     real data). Prod has real data: never run an untested migration on it. Rollback = the dump,
     the old backend folder, the web copy and the tagged image.
11.10 Tests that create dated receipts must use a year that is UNIQUE to that test, because the test
     database keeps its rows between runs and a fixed year or number would collide. Do NOT rely on an
     unseeded random year: two tests can draw the same year, the receipt counter is then already advanced
     and the test flakes (this is what made test_number_formats fail with "expected 0001, got 0011").
     Give each test a distinct far-past year reserved for it (e.g. a module-level counter), or seed the
     randomness, so a year can never repeat within a run.
11.11 ALL MODULES ARE BUILT AND ACTIVE: db/seed_defaults.py NOT_BUILT_YET is empty (NOT_BUILT_YET = ()).
      Every module in MODULE_AREAS has status = True (magazines in 0064, events and engagements in
      0067, reports in 0068, notifications in 0069, imports in 0070). If a new module is ever introduced,
      follow the full lifecycle: define it in MODULE_AREAS, add its pages to MENU_PAGE_CATALOG, create
      its privileges in SUB_MODULE_AREAS, write an Alembic migration switching it on for existing
      databases, and verify tests/test_screen_privileges.py and tests/test_sidebar_has_no_dead_items.py.
11.13 PROD IS LIVE: ITS DATA CHANGES BETWEEN UPDATES (users, roles, receipts, privileges are edited
     there by the office). Always take a FRESH backup and look at the live rows right before an
     update; never copy UAT data or role settings over prod; a migration must not undo what the
     office changed (it may only add privileges, never remove ones the office gave). Fix prod data
     through the app's own API (audit log), not by editing tables, and say what was changed.
11.14 UAT AND PROD RUN THE SAME COMMIT. After any prod update the live web bundle name and the
     alembic version must be identical on both; check both and report them.
11.15 SHARED WORKING TREE: other agents edit the same files at the same time. Commit only the files
     you changed, never `git add -A`, and never add a file another agent has unsaved edits in:
     build the HEAD version plus only your lines (git hash-object -w, git update-index --add
     --cacheinfo) instead. A migration chains after the real head; if the previous one is another
     agent's and not committed, commit that file with yours so HEAD stays one chain. Before a deploy
     export HEAD (git archive HEAD backend frontend REMEMBER.txt), run the tests and the build on that
     export: what is committed must work alone.
11.16 DEPLOY CHECKS: build the web files from HEAD, not from the working tree. In Git Bash set
     MSYS_NO_PATHCONV=1 for `vite build --base=/` (otherwise the base becomes C:/Program Files/Git/
     and every page loads a blank screen with "Expected a JavaScript module"). Use the IP that the
     site's own name resolves to (nslookup), never an old VPS_HOST. After a deploy fetch the page's
     /assets files and confirm each answers 200 with the right content type. A prod web-only update is
     built from prod's own commit plus only the asked files: first rebuild prod's CURRENT bundle and
     match its file name, then apply the change.

RULE 12: UI STANDARDS (PAGES, POPUPS, BUTTONS, BOTTOM BARS)
--------------------------------------------------------------------------------
12.1 PAGE HEADING AND FRAME:
     - Every page starts with ONE plain heading in the same place and size:
       <h1 className="text-xl sm:text-2xl font-bold text-[#180200] tracking-tight">.
       No breadcrumb, no icon tile, no big sub-heading, no description block. At most one
       small text-xs line under it when the page really needs a warning.
     - The page wrapper is a single column with space-y-6. No Back button on a page: the
       sidebar and the parent page already lead back.
     - Action buttons for the page (Add, Export, Day Book ...) sit on the right of the
       heading row. The search box also goes in that row when the page has one
       (SearchFilterBar with searchInHeader). Filters sit in one row below it with a
       Reset Filters button.
12.2 FONTS: normal site sizes only. Body and table text text-sm or text-xs, labels and help
     text text-xs, table headers text-[10px] uppercase tracking-wider. Never enlarge a
     font to fill space. Page headings are the only large text.
12.3 POPUPS (MODALS):
     - Use components/Modal.jsx. The header bar and the footer bar are the same height
       (h-14). The footer is ALWAYS components/ModalFooter.jsx, never hand-made buttons.
     - Footer = Cancel (outline) on the left of ONE main button, equal size, text only,
       right-aligned. The main button label follows the kind: add -> Save, edit ->
       Update, delete -> Delete (red), confirm -> Confirm. A view-only popup has a single
       Close button. A special verb (Restore, Generate ...) uses submitLabel.
     - While saving the main button shows its busy label (Saving..., Updating...) and both
       buttons are disabled.
12.4 CONFIRMATIONS: every action that changes data asks for a confirmation and a reason
     (SweetAlert, class hms-mini-swal) through the shared api client; the reason goes to
     the activity log. Destructive actions use the red button. Irreversible bulk actions
     (Data Cleanup) also need the confirm word typed. Do NOT add success popups after
     routine actions (Assign, Unassign): use a short toast (utils/notify) or nothing.
12.5 BOTTOM ACTION BARS AND FORM BUTTONS:
     - Form buttons are right-aligned at the bottom: Reset (not Cancel) on entry forms,
       then Save, with Save & New / Save & Close where the flow needs them. No Save & Print.
     - A long selection page (Data Cleanup) keeps its action bar sticky at the bottom, with
       the selected count on the left of the main button.
12.6 TABLES AND LISTS:
     - Counts, statuses and flags are small chips (chip, chip-on, chip-warn, chip-bad,
       chip-brand, chip-off), never long sentences.
     - A missing value shows a faint dash or "Not recorded yet". Never invent a value such
       as "Standard", "Member", "Cash" or "Online" to fill a gap.
     - Empty state is one short line. Rows with nothing to act on are greyed and their
       checkbox disabled.
     - Batch checkboxes follow rule 5.2 (a Select toggle), except pages that are selection
       pages by nature (Data Cleanup, Recycle Bin).

RULE 13: PERMISSIONS AND ACCESS
--------------------------------------------------------------------------------
13.1 EVERY API ROUTE CHECKS A PRIVILEGE. tests/test_every_route_is_guarded.py calls all
     routes as a user with no privileges and expects 403, except an allow-list (docs, login,
     own account, token links, sidebar menu, /meta lists, the mobile-app requests). A new
     route that is open on purpose goes into that list with the reason; otherwise it must
     use require_permission.
13.2 THE SCREENS HIDE, THEY DO NOT GREY OUT. A button or link the role has no privilege for
     is removed ({hasPermission('x') && ...}), not shown disabled with a tooltip. The save
     handlers also check the privilege, because Enter inside a field still submits a form.
13.3 STATUS (ACTIVE / INACTIVE) PILLS stay visible but cannot be clicked without the
     screen's .write privilege. There is no separate status privilege.
13.4 SIDEBAR: a page shows only when the role holds its privilege; a group (Masters,
     Receipts ...) shows only when at least one page inside it shows. A parent follows its
     children automatically. A disabled module is hidden for everyone.
13.5 SUPER ADMIN ONLY AREAS (rank 0) stay rank-gated and get NO grantable privilege: the
     Modules page, Menu Arranger, and the Settings group (min_rank_level 0). Do not add
     privileges for them. Data Cleanup has privileges (system.cleanup.read / write) but is
     also locked to rank 0 roles.
13.6 USERS AND ROLES (rank 0 = Super Admin, hidden and never named on any screen; rank 1 = Admin, the top
     anyone else sees; bigger = weaker). NEVER show a rank number, rank gate or 'higher rank' wording in the UI
     or in error messages; new roles are created at 99 (no rank field on the role form):
     - User Management lists staff accounts of your own rank or weaker (members are never
       users); see rule 13.10. A rank 0 user sees everyone.
     - Changing a user (edit, status, delete) needs the target to be the same rank or weaker.
       This includes rank 0: a Super Admin may create and manage another Super Admin (a
       lower rank never can). Stronger users' rows show locked buttons.
     - Roles list and edit only roles strictly weaker than yours, never your own rank. The
       roles you may GIVE to a user are your own rank and weaker.
     - Nobody changes their own role. The built-in admin account is changed only by the
       Super Admin, and the last active top-rank holder cannot be removed.
13.7 PRIVILEGE CODES OF THE SETTINGS TOOLS: masters.organisation.read/write (Organisation
     Settings), system.number_formats.read/write, system.recycle_bin.read/write,
     system.cleanup.read/write. Each is also a sub-module in services/permission_areas via
     SUB_MODULE_AREAS in db/seed_defaults.py.
13.8 ADDING A SCREEN (checklist, always all of it):
     a. Sidebar page: a row in MENU_PAGE_CATALOG (db/seed_defaults.py) with its parent,
        route, icon (a name from utils/menuIcons.js), order and the privilege that shows it.
        A tool reached only from another page (Recycle Bin) is a module row with no route.
     b. Privileges: the screen's own read / write (/ delete) in SUB_MODULE_AREAS with its API
        path prefix, plus AREA_ACTIONS when it does not have all three. The routes keep
        asking for the module code (system.read); services/permission_areas maps it.
     c. A migration that seeds the modules, menu pages and privileges for existing databases
        and, when the screen replaces an older privilege, grants the new one to the roles
        that held the old one (see 20261013_0055 and 0057). Take the next free number.
     d. Frontend: the route in App.jsx wrapped in PermissionGate (page) and hasPermission
        on every action (rule 13.2).
     e. Tests: the privilege tree shows the new codes, the sidebar shows or hides the page,
        and test_every_route_is_guarded still passes.
13.9 RANK GATE OF A MODULE OR PAGE (Modules page, "rank gate" = min_rank_level):
     - Rank N means only roles ranked N or better (smaller number) can see or use it.
       Empty means no rank limit: then only the privilege decides.
     - A module is only as reachable as every module above it. A rank 1 module makes ALL
       its pages and sub-modules rank 1, whatever they say. A page may be stricter than its
       module (rank 1 page under a rank 2 module), never looser.
     - The sidebar, the server (require_permission) and the Roles & Privileges table all
       follow this. The privilege table uses the strictest rank along the path, so rows a
       role's rank cannot reach are not listed for it.
     - A page with BOTH an empty rank gate AND no privilege is shown to every signed-in
       user. Always set at least one of the two.

13.10 WHO YOU CAN SEE IN USER MANAGEMENT: only users whose role is your own rank or weaker.
      A stronger rank is never listed and never opened (a rank 2 Admin does not see the
      Super Admin). Opening, editing or deleting a stronger user answers 404 "User not found",
      exactly like a user that does not exist (see 13.18). A rank 0 user sees everyone else. Your OWN account is not listed: you cannot
      change your own role or privileges, and My Profile edits your details.
13.11 ROLE DATA IN THE SCREENS: GET /users/roles returns each role with permission_codes
     (the privilege codes it holds) and is_all_access. A full-access role holds no
     individual privilege rows, so show "All privileges" / "Every module" for it. Never read
     a field called `privileges` on a role. The roles list only holds roles you may assign
     (the Super Admin role is not in it for lower ranks), so a user's role name and rank
     come from the user row (role_name, role_rank_level), not from a lookup in that list.
13.12 LOGIN: the username is the login ID (email and mobile do not log in). It must be
     unique, is shown as the display name in the top bar, and changing it signs the person
     out. Dates and last login come from created_at / last_login_at (snake_case) as the
     server sends them.
13.13 NEEDS APPROVAL CASCADING & UNIFIED APPROVALS SCREEN:
     - In Roles & Privileges, selecting "Needs approval" on a parent module row automatically
       cascades to all active child sub-modules under that subtree; setting it to "Direct" also
       cascades to all children. Parent badge shows "Needs approval", "Needs approval (Some)",
       or "Direct".
     - The Approvals screen (/dashboard/approvals) displays all approval actions in ONE unified

      page that owns the data. A button, link or redirect to something the role cannot open is

     the import makes; 140 lines, Rs 14,000 on UAT, services/legacy_import.py _AMRUTHA, scripts/legacy_retag_amrutha.py).
     PATRIKA FUND / PATRIKA NIDHI notes stay Patrika Nidhi. Receipt totals never change by a move.
16.3 REGISTER RECEIPTS. Every register record is a receipt of its own. A number used again in the SAME financial year
     keeps the earliest record; the others get /2, /3 ... (a number is unique per financial year, so the same number
     in ANOTHER year is simply another number). A line with no date is not imported; a date before 1943 or in the
     future is not imported; no number (or one already taken on another date) gets a made-up number FY<yy>-<nnn>,
     marked is_old_receipt (shown UNKNOWN). The register's numbers are never changed to hide a repeat: the office
     corrects one by editing the receipt. REPEATED RECEIPT NUMBERS page (Receipt Tracking > the repeat icon,
     /dashboard/receipts/repeats, GET /receipts/repeats): a back icon and a search, each number is a heading with every
     record that used it under it, each record has View and Edit (Edit opens in a NEW TAB). The receipt popup shows one
     plain line "Same number also used by:" (GET /receipts/{id}/same-number). No colours, no REPEAT tags on the list.
16.4 GENDER IS NEVER GUESSED. Only the title says it: SRI = male, SMT. / KUM. = female, anything else (DR., PROF. ...)
     stays blank. The new member form and the children rows start with NO gender (no default Male); the title still
     moves the gender, and the gender moves the title.
16.5 NAMES ARE NOT SPLIT. An imported name is kept whole in full_name_en and first_name_en; middle and last stay empty
     (rule 15.22 for typed ones). A name such as UMA is a valid name: there is no "name too short" check.
16.6 PLACE COMES FROM OUR OWN DATA. State, district and taluk are taken from our postal-code row for the pincode; the
     file's CusState / CusDistrict / CusTaluk are ignored (the state is a fallback only when the pincode is unknown). A
     row with the pincode and post columns swapped is read right (services/legacy_import.py _pin_and_post). On the member form the
     place is picked top-down as searchable lists that open downward: State > District > Taluk > Pincode / Post office.
     "Locality / Area" is READ ONLY and fills from the picked post office (the B.O / S.O / H.O ending removed). There is
     no Native Place box and no Employment box: one "Occupation / Designation" field (designation).
16.7 GUARDIAN. CusRelation G puts the name in members.guardian_name (its own field, shown as Guardian); S/O, W/O, D/O
     put it in father_husband_name with the prefix ("S/O RAMA BHAT"). A guardian is not counted as a family member.
16.8 THE MAGAZINE. (a) CusMagazine = No means NO magazine, whatever else the row says (Online / Print, the type and the
     receipts are all ignored for it). (b) THE MAGAZINE NEEDS NO EMAIL: magazine_email is never kept, imported or shown
     (an e-copy is read on the site); the member's own email is separate. (c) AN EXPIRED OR DELETED (INACTIVE) MEMBER
     NEVER GETS A SUBSCRIPTION STARTED, not by approval, an edit, a receipt or the backfill, and is never listed in the
     "paid members requested the magazine but have no active subscription" banner (services/magazine_subscriptions.py).
     The import starts a subscription only for ACTIVE, approved members.
     (d) AN APPLICANT WHO HAS PAID IS ON THE LIST (the user's decision, 30-Oct-2026): an unapproved applicant who said Yes gets an
     ACTIVE subscription the day a receipt is assigned to them (services/magazine_subscriptions.has_paid), is printed on the labels
     and counted in the pending labels report; a REJECTED applicant's subscription is stopped (their receipts are unassigned).
     (e) NOTHING IS HELD BACK FOR NOT PAYING: the label run has no "paid only" box. The subscription decides who is listed, so an
     approved member with no receipt linked (an old member whose receipt is missing) still gets the magazine. The pending labels
     report lists exactly who the next run would print.
16.9 BLOOD GROUP IS ONE FORM: A+, A-, B+, B-, AB+, AB-, O+, O-. core/blood_group.py turns "O+VE", "A +VE", "AB -VE",
     "b+" into it on every save and import; scripts/legacy_normalize_blood_group.py fixes stored ones. A bare "A" or "AB"
     (no sign) is left as typed.
16.10 THE DATES OF A MEMBER (services/member_dates.py; one place, used by every screen; nothing is stored):
      - IMPORTED, approved: Registered on and Member since = the date of the FIRST receipt that is not cancelled; with no
        receipt, the register's own enrolled date when it is a real one (the import stamps the import day on a membership
        with no enrolled date: that is not real); otherwise EMPTY. Approved on is EMPTY (the import approved everybody on
        one day). The import day is shown only as "Imported on" (imported_on), never as the member's date.
      - IMPORTED applicant: Registered on = the register's enrolled date, else the first receipt; no approval, no member since.
      - ANY OTHER member: Registered on = the day the form was registered, Approved on = the approval day, Member since =
        the approval day; not approved yet = no approval and no member since.
      The profile, the lists, the Unapproved popup and Receipt Entry read registered_on / approved_on / member_since from the
      server. VALID TILL / EXPIRY IS NOT SHOWN ANYWHERE (rule 15.1); the data stays stored.
16.11 STORED DATA IS READ AS IT IS. The typed-in rules (at least 18 years old, mobile and alternate number shape, blood
      group form) belong to the INPUT schemas (MemberBase, MemberCreate, MemberUpdate), never to the response (MemberFields /
      MemberInDBBase). An imported child or a short alternate number must still open (it caused an internal server error on
      Edit for 7,354 members). The ALTERNATE NUMBER may be a landline: digits with a space or a dash (an STD code), 6 to 15
      digits; the main mobile stays 10 to 12 digits.
16.12 DATE OF BIRTH IS TYPED AND SHOWN AS DD-MM-YYYY EVERYWHERE: use components/DateInput.jsx (never a raw type="date" box,
      which follows the computer's format); Excel files write it as DD-MM-YYYY text.
16.13 DATA CHECK (Membership List > Data Check, /dashboard/membership/data-check, GET /data-check/members, privilege
      members.list.read; services/data_check.py). One tab per problem: date of birth in the future, under 18, over 110,
      alternate number not 10 to 12 digits, wrong email, no pincode or district, printed magazine with no address, no
      date of birth, no mobile number, no address. Each tab has search, paging (200 max), Excel, a KYC column and filter
      (All / Not verified / Verified), the KYC popup and an Edit button that opens in a new tab. By decision it has NO tab
      for: an online magazine with no email, active/inactive against expiry, a short name, odd characters in a name.
16.14 THE KYC POPUP (components/VerifyMemberModal.jsx, also on Duplicate Members): wide (max-w-5xl), the call outcome and
      remark on top, then three cards: Identity (name, gender, date of birth, father / husband, guardian), Contact (mobile,
      WhatsApp, alternate number, email, how the magazine reaches them: not needed / online / printed) and Address (lines
      1 and 2, state, district, taluk, locality, pincode / post office). It opens at the box the list is about. It saves
      through the normal member update (same rules, same approval gate).
16.15 THE MEMBER PROFILE. The Personal Details tab lists EVERY field and shows a dash for an empty one (so Aadhaar and the
      rest are always there); the Overview stays brief and hides empty rows (rule 12.11). There is no Print profile button.
      The quick-facts strip is Member since, Last receipt, Payment.
16.16 NO DATABASE ID ON ANY SCREEN (rule 1.1): not in the Assign a receipt popup (name and mobile only), not in the user
      list, nowhere. Test a new screen for it.
16.16a AN AADHAAR NUMBER TYPED INTO A REGISTER NOTE IS SEEDED INTO THE AADHAAR NUMBER BOX AND TAKEN OUT OF THE NOTE (the user's rule,
      31-Oct-2026: "seed the Aadhaar number if it is entered", never just delete it). 125 members had it, mostly in the magazine
      note (CusNoteMagazine), a few in the status note. services/legacy_import.split_aadhaar finds a label (Aadhaar / Adhar / Aadhaara,
      "no", ":") and takes the number only when it is exactly 12 digits; the rest of the note ("Return 11-08-2025") stays; a number
      that is not 12 digits stays in its note, nothing is invented. A member who already has a number keeps it (a different one in the
      note is counted as a conflict). The import does it for new members; scripts/legacy_backfill_aadhaar.py MstMember.xlsx does it for
      members already imported (safe to repeat). Never use `number` for anything but the membership number inside the import loop.

16.17 FILE FORMATS ARE SHOWN, FROM THE SERVER. Every import popup / card has a "File format" box: what the file is, a
      "See every column" list and a format file to download. The columns come from the server, so the screen and the
      import cannot disagree: /meta/import-format/members (the CSV), /members/legacy-import/format and /template
      (MstMember), /members/unapproved-applications/import/format and /template (MstApplication). The format file's
      first sheet holds only headings (uploading it unchanged imports nobody); a second sheet explains each column.
